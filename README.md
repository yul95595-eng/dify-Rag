# 企业智能问答与工单分类助手（轻量级 RAG 原型）

> **重要声明**：本项目全部知识库内容均为**示例模板**，基于公开的企业制度范本、行政后勤手册、IT 服务台 FAQ 等资料改写整理，**不代表任何真实企业的实际制度**。文中所有天数、金额、比例、时限均为「示例数值」，不含真实企业名称、真实电话、真实邮箱、真实网址。用于真实场景前，请替换为本企业经审批的正式制度文本。

---

## 1. 项目简介

### 1.1 项目目标

搭建一个轻量级 RAG（检索增强生成）原型，帮助员工快速查询公司制度、办事流程与服务窗口，并自动判断咨询所属类别，返回处理建议。当知识库无法可靠回答时，输出固定转人工话术，避免大模型编造制度。

### 1.2 核心能力

| 能力 | 说明 |
| --- | --- |
| 工单自动分类 | 将员工问题归入 6 个类别之一：`人事`、`行政`、`财务`、`IT`、`后勤`、`其他` |
| 制度问答 | 仅依据知识库检索结果作答，标注引用来源（`文档名#章节名`，同名不重复拼接） |
| 多轮问题改写 | 追问场景下用历史对话补全指代（v2.0 新增，首轮逐字原样透传） |
| 工单字段扩展 | 额外输出 `priority`（紧急度）、`department`（归口部门）、`summary`（一句话摘要） |
| 兜底转人工 | 无可靠依据时输出固定话术：`暂未找到明确制度，建议转人工处理。` |
| 处理建议 | 每条回答附带 `suggestion`，指明办理渠道与需准备材料的概括性描述 |
| 离线评估 | 65 条测试问题批量回归，输出准确率、每类 P/R/F1、混淆矩阵、兜底率 |
| 合规拦截 | 命中「他人隐私 / 他人薪酬」等敏感诉求时直接拦截并转人工，不进入知识库检索（v3.0 新增） |
| 自适应检索重试 | 首检零召回且分类非「其他」时，自动改写问题二次检索，仍无召回才兜底（v3.0 新增） |
| 情绪识别与语气适配 | 独立情绪节点识别「平静 / 不满 / 焦急」；不满或焦急时回答先给一句共情开场白（v3.0 新增） |
| 工单闭环 | 兜底 / 合规 / 转人工场景输出 `ticket_id`（`GD-` + 8 位十六进制）与 `sla` 响应时限（v3.0 新增） |

### 1.3 最终输出结构

工作流对每个问题返回一个 JSON 对象。v1.0 为 6 字段，v2.0 起扩展为 9 字段，**v3.0 起扩展为 15 字段**（当前线上版本 v3.2）：

```json
{
  "question": "年假怎么申请？需要提前几天提交？",
  "category": "人事",
  "priority": "低",
  "department": "人力资源",
  "summary": "咨询年假申请流程与提前提交时限",
  "answer": "年休假需提前在OA系统申请，单次最小单位为半天……（依据知识库生成）",
  "suggestion": "请通过OA系统提交年休假申请，并根据请假天数提前相应时间提交。",
  "source": "leave_policy.md#2.1 年休假;leave_policy.md#3. 请假审批流程",
  "need_human": false,
  "sentiment": "平静",
  "risk_flag": 0,
  "is_compliance": 0,
  "compliance_reason": "",
  "ticket_id": "",
  "sla": ""
}
```

兜底场景：

```json
{
  "question": "公司食堂的供应商是哪一家？联系方式是什么？",
  "category": "其他",
  "priority": "低",
  "department": "后勤服务台",
  "summary": "咨询食堂供应商信息与联系方式",
  "answer": "暂未找到明确制度，建议转人工处理。",
  "suggestion": "该问题暂未被知识库覆盖，建议提交人工工单：说明问题背景、发生时间、涉及部门与期望处理时限，由对应归口部门跟进答复。",
  "source": "none",
  "need_human": true,
  "sentiment": "平静",
  "risk_flag": 0,
  "is_compliance": 0,
  "compliance_reason": "",
  "ticket_id": "GD-6417854A",
  "sla": "3 个工作日内响应"
}
```

> 字段说明：`priority` 仅判定紧急程度，**不参与也不影响 `category` 判定**（v2.1 已在提示词中做规则隔离）；
> `department` 为建议归口部门；`summary` 为一句话工单标题。9 个基础字段由 `code_parse` 统一解析并做容错兜底。
>
> v3.0 新增 6 字段说明：
> `sentiment`（`平静` / `不满` / `焦急`，由独立节点 `pe_sentiment` 产出，仅用于语气适配，不改变事实内容与判定结果）；
> `risk_flag`（0/1，标记问题是否含申诉、纠纷、举报、安全等高敏诉求）；
> `is_compliance` 与 `compliance_reason`（合规拦截标记与原因，命中「他人隐私 / 他人薪酬」时为 1）；
> `ticket_id`（工单号，`GD-` + 8 位大写十六进制）与 `sla`（响应时限，高 2 小时内 / 中 1 个工作日内 / 低 3 个工作日内），
> **仅在三类需要人工承接的场景（兜底、合规拦截、转人工）生成，正常问答路径为空字符串**。

## 2. 数据准备方式

### 2.1 资料来源

> 完整的检索策略、来源链接清单与提炼要点见 **`research_summary.md`**。

知识库内容通过联网检索公开资料整理，主要来源类型：

- 各级政府公开文件与法规解读（如职工带薪年休假条例、医疗期规定、电子发票报销入账归档相关规定）
- 公开的企业员工手册模板、人事行政管理制度范本
- 公开的财务报销与差旅费管理办法模板
- 公开的 IT 服务台 FAQ、企业信息化运维手册
- 公开的行政后勤管理手册、物业与食堂宿舍管理规范

### 2.2 数据脱敏与规范化处理

所有文档在生成时统一执行以下处理，保证可安全用于原型演示：

1. **去真实主体**：不出现任何真实企业名称、真实人名、真实部门电话、真实邮箱、真实外部网址；涉及渠道时只写内部系统通用名称（OA、IT 服务台工单系统、后勤服务平台）。
2. **数值示例化**：所有具体天数、金额、比例、时限统一标注为「示例数值」，并在文档头部声明；回答节点提示词中强制要求保留「示例」表述。
3. **结构化改写**：按「制度目的 → 适用范围 → 具体规则 → 流程步骤 → 注意事项 → FAQ」重组，标题层级清晰（`#` / `##` / `###`），便于按标题切分 chunk。
4. **表格化**：审批权限、报销标准、SLA 时效、假期天数等强规则内容一律使用 Markdown 表格，提升检索片段的自解释性。

### 2.3 替换为真实数据的步骤

1. 用本企业经审批的正式制度文本替换 6 份 `.md` 文件内容，保持标题层级结构不变。
2. 删除各文档头部的「示例模板」声明段落，并去掉正文中的「示例数值」标注。
3. 在 `dify_prompts.json` 的回答节点提示词中，删除关于「保留示例表述」的第 4 条规则。
4. 重新在 Dify 知识库中导入并重建索引（见第 3 节）。
5. 按真实业务补充 `test_questions.json`，重点补充易混淆的边界问题。

## 3. Dify 知识库配置建议

### 3.1 前置准备

在开始配置前，需确认 Dify 环境满足以下条件：

- **已安装并配置至少一个模型供应商**（左侧导航 `集成` → `模型供应商`，即 `/integrations/model-provider`；旧版路径为 `设置 → 模型供应商`）。若列表为空，先点「安装模型供应商」从 Marketplace 装一个可用的 LLM 插件并填入 API Key，否则工作流无法运行。
- **已配置 Embedding 模型**（知识检索必需）。
- **可选：配置 Rerank 模型**，能显著提升多文档召回的精度。

### 3.2 创建知识库

> 完整的 14 步操作说明、注意事项与排障表见 **`dify_knowledge_base_setup.md`**，本节为速查摘要。

1. 进入 `知识库 → 创建知识库`，命名为「**企业制度知识库**」。
2. 数据源选择「导入已有文本」，上传 6 份 Markdown 文档：`employee_handbook.md`、`leave_policy.md`、`reimbursement_policy.md`、`it_faq.md`、`admin_service.md`、`logistics_service.md`。
3. **分段策略**：需求指定「自动分段」可直接使用；但本项目 6 份文档均为规整 Markdown，**推荐改用「自定义」**以获得更干净的语义边界：
   - 分段标识符：`\n## ` 或 `\n### `（按 Markdown 标题层级切分，让每个 chunk 对应一个完整制度小节）
   - 分段最大长度：`500 - 800` tokens
   - 分段重叠长度：`80 - 100` tokens
4. **索引方式**选择「高质量」（向量索引），并开启 Embedding 模型。
5. 点「保存并处理」，等待全部文档状态变为「可用」。
6. 在「召回测试」中输入 6 类各一个典型问题，验证片段是否命中正确文档。

### 3.3 检索设置建议

| 配置项 | 需求指定值 | 本项目实际线上值 | 说明 |
| --- | --- | --- | --- |
| 检索模式 | 混合检索 | **混合检索**（`retrieval_mode: multiple`，一致） | 制度类文本含大量专有名词，关键词召回不可缺 |
| Top K | 5 | **5**（一致） | 未部署 Rerank 时可提高到 `6 - 8` |
| Score 阈值 | 0.5 | **0.5**（一致，已开 Rerank） | 阈值过低会引入噪声导致编造，过高会频繁触发兜底 |
| Rerank | 开启 | **开启**（模型 `qwen3-rerank`，一致） | 显著提升跨文档场景的排序质量 |
| 索引方式 | — | 高质量（`high_quality`），Embedding `text-embedding-v4` | 6 份文档全部 `completed` / `enabled`，共 29957 字 |
| 引用与归属 | — | 建议开启 | 便于核对 `source` 字段，也方便人工回溯 |

> **当前配置已实时核验**：知识库「企业制度知识库」（ID `7fd1477b-cf23-46e9-ab28-7aedc512d44a`）的库级 `retrieval_model_dict` 与工作流 `kr` 节点参数完全一致，均为混合检索 / Top K 5 / 阈值 0.5 / Rerank 开启，v2.0 与 v2.1 优化过程中**未做任何改动**。

> **关于阈值 0.5 的重要提醒**：`0.5` 只有在 **Rerank 模型真正生效**时才安全。若实例上没有可用的 Rerank 模型，混合检索的原始分数通常落在 `0.2 ~ 0.45`，阈值 0.5 会过滤掉绝大部分正确片段，导致几乎所有问题都走兜底分支。
>
> **定阈值的可靠方法**：把阈值临时设为 `0`，在「召回测试」里跑 6 类各一题，记录正确片段的实际分数，取其最低分的 80% 作为阈值。详见 `dify_knowledge_base_setup.md` 第 3.1 节。

### 3.4 元数据过滤（进阶）

为每份文档添加元数据字段 `category`，取值对应主责类别：

| 文档 | category 元数据 |
| --- | --- |
| `employee_handbook.md` | 人事 |
| `leave_policy.md` | 人事 |
| `reimbursement_policy.md` | 财务 |
| `it_faq.md` | IT |
| `admin_service.md` | 行政 |
| `logistics_service.md` | 后勤 |

在知识检索节点中按分类结果做元数据过滤，可缩小检索范围、提升精度。原型阶段也可先用单个全库检索节点，跑通后再优化。

## 4. Dify 工作流节点说明

### 4.1 应用类型

推荐创建 **Chatflow（对话流）** 应用；若只做单次无上下文调用，也可用 **Workflow**。应用名建议：`企业智能问答与工单分类助手`。

### 4.2 工作流拓扑

> 以下为**当前线上版本（v3.2）**的实际拓扑，共 **27 节点 / 32 边 / 3 个 if-else**。
> 版本对比：v1.0 为 13 节点 / 13 边；v2.x 为 15 节点 / 15 边；v3.0 起扩到 27 节点 / 32 边并新增三条分支。

```
start(query, files)
   │
   ▼
code_question ──→ 归一化问题文本，拼接历史对话摘要（多轮上下文入口）
   │
   ▼
llm_rewrite ──→ 用历史对话补全指代；无历史时逐字原样输出
   │
   ▼
code_rewrite ──→ 改写守卫：扩写超过 max(len(原句)+8, len(原句)*1.35) 即回退原句
   │
   ▼
code_compliance ──→ 确定性合规闸门（词表+规则，非 LLM）：识别「他人隐私 / 他人薪酬」等敏感诉求
   │
   ▼
ifelse_compliance（OR 条件）
   │
   ├──── true（命中敏感）───────┐
   │                            ▼
   │              llm_compliance_hint（只产出合规提示，严禁作答敏感内容）
   │                            ▼
   │              code_compliance_merge ──→ 固定话术 + 工单号 + SLA
   │                            ▼
   │              answer_compliance（直接回复）
   │
   └──── false（正常路径）───┬────────────────┬────────────────┐
                            ▼                ▼                ▼
                     pe_category        kr（知识检索）   pe_sentiment（情绪识别）
                     输出 category       混合检索 Top K 5   平静 / 不满 / 焦急
                     + priority          阈值 0.5
                                         Rerank qwen3-rerank
                            │                ▼
                            │        code_context ──→ 拼装上下文、统计 retrieval_hit、
                            │                │        生成来源白名单（文档名#章节，去冗余）
                            │                ▼
                            │        ifelse_requery（AND 条件）
                            │                │
                            │      ┌─────────┴─────────┐
                            │  true（零召回且非「其他」）  false
                            │      ▼                  │
                            │  llm_requery            │
                            │      ▼                  │
                            │  code_requery_check     │
                            │      ▼                  │
                            │  kr2（二次检索，配置与 kr 逐字一致）
                            │      ▼                  │
                            │  code_context2          │
                            │      └────────┬─────────┘
                            │               ▼
                            └──────→ code_ctx_merge ──→ 两组检索结果择一（正常路径与 v2.1 完全一致）
                                            ▼
                                     llm_answer ──→ 仅依据上下文作答，输出 9 字段 JSON（含情绪语气适配）
                                            ▼
                                     code_parse ──→ 解析 + 容错兜底，产出 15 字段
                                            ▼
                                     ifelse_human（OR 条件）
                                            │
                            ┌───────────────┴───────────────┐
                            │ true（需转人工）              │ false（正常回答）
                            ▼                               ▼
                     llm_fallback                     code_ok_merge
                     （只生成 suggestion，                  ▼
                      禁止改动固定话术）              answer_ok（直接回复）
                            ▼
                     code_fb_merge ──→ 固定话术「暂未找到明确制度，建议转人工处理。」
                            │           + need_human=true + 工单号 + SLA
                            ▼
                     answer_fb（直接回复）
```

`ifelse_compliance` 的 true 分支判定（`logical_operator = or`，任一命中即拦截）：

| 条件 | 含义 |
| --- | --- |
| `code_compliance.is_sensitive = 1` | 命中他人隐私 / 他人薪酬等敏感诉求，直接拦截 |

`ifelse_requery` 的 true 分支判定（`logical_operator = and`，两个条件同时满足才重试）：

| 条件 | 含义 |
| --- | --- |
| `code_context.retrieval_hit = 0` | 首轮检索零召回 |
| `pe_category.category is not 其他` | 且问题有明确制度归属（「其他」类无需重试，直接兜底） |

`ifelse_human` 的 true 分支判定（case_id `true`，OR 关系，任一命中即转人工）：

| 条件 | 含义 |
| --- | --- |
| `code_parse.is_fallback = 1` | 回答节点已输出固定兜底话术 |
| `code_parse.need_human = 1` | 涉及申诉、纠纷、举报、紧急安全等必须人工的场景 |
| `code_ctx_merge.retrieval_hit = 0` | 知识检索（含重试后）仍无有效召回 |
| `pe_category.__is_success = 0` | 分类节点执行失败（模型异常/超时） |

### 4.3 节点详解

| # | 节点 ID | 类型 | 关键配置 | 作用 |
| --- | --- | --- | --- | --- |
| 1 | `start` | 开始 | 系统变量 `query`、对话历史 | 接收员工自然语言问题 |
| 2 | `code_question` | 代码（Python） | 文本归一化 + 历史摘要拼接 | 为改写节点准备输入 |
| 3 | `llm_rewrite` | LLM（`qwen3.7-max`） | temperature = 0.1、top_p = 0.9；「无历史对话时逐字原样输出」 | 多轮场景补全指代（v2.0 新增） |
| 4 | `code_rewrite` | 代码（Python） | 扩写比例守卫，超限回退原句 | 防止改写节点自由发挥（v2.1 加固） |
| 5 | `pe_category` | 参数提取器 | 6 类别 + 10 条边界规则 + 15 条 few-shot | 输出 `category`、`priority` 与 `__is_success` |
| 6 | `kr` | 知识检索 | 混合检索、Top K = 5、阈值 = 0.5、Rerank = `qwen3-rerank` | 召回制度片段（**需求指定参数，未改动**） |
| 7 | `code_context` | 代码（Python） | 拼装上下文、统计 `retrieval_hit`、来源白名单去冗余、相关度读 `metadata.score` | 约束 `source` 只能取真实片段 |
| 8 | `llm_answer` | LLM（`qwen3.7-max`） | temperature = 0.1；7 条防幻觉护栏 + 情绪语气适配块 | 仅依据上下文作答，输出 9 字段 JSON |
| 9 | `code_parse` | 代码（Python） | JSON 解析容错（裸 JSON / 代码块包裹 / 纯文本） | 产出 15 字段 + `is_fallback` |

| 12 | `code_fb_merge` | 代码（Python） | `FALLBACK` 常量产出固定话术，`need_human = true`，附工单号 + SLA | 保证话术逐字一致、可被脚本精确匹配 |
| 13 | `answer_fb` | 直接回复 | 引用 `code_fb_merge` 输出 | 返回兜底 JSON |
| 14 | `code_ok_merge` | 代码（Python） | 组装正常回答 JSON | 统一输出结构 |
| 15 | `answer_ok` | 直接回复 | 引用 `code_ok_merge` 输出 | 返回正常回答 JSON |

**模型统一说明**：5 个 LLM 节点（`llm_rewrite` / `llm_answer` / `llm_fallback` / `llm_compliance_hint` / `llm_requery`）与 2 个参数提取器（`pe_category` / `pe_sentiment`）均使用供应商 `langgenius/tongyi/tongyi` 的 **`qwen3.7-max`**；Embedding 为 `text-embedding-v4`，Rerank 为 `qwen3-rerank`。切换前使用的 `qwen3.8-max` 因额度用尽被 Dify 包装为 `Incorrect model credentials provided` 报错（详见第 8 节 FAQ）。

### 4.4 分类节点（pe_category）

- **类别定义**与**边界规则**：提示词内共 **10 条归类边界规则**，重点覆盖易混淆场景：
  - 账号开通 / 密码 / 网络 / 邮箱 / 软件安装 → 一律归 `IT`，即使出现在入职场景中
  - 电脑、打印机、网络设备故障 → `IT`；门窗、家具、空调、电梯、水电线路 → `后勤`
  - 工牌门禁、会议室、办公用品、快递 → `行政`；宿舍、食堂、停车、维修、保洁 → `后勤`
  - 索取真实电话 / 邮箱 / 网址、知识库未覆盖内容 → `其他`
  - 闲聊 / 写诗 / 翻译 / 编程等与企业制度无关的请求 → `其他`
  - 主观人际咨询（见下）→ `其他`
- **v2.1 新增排除规则**（修复 Q064 误判）：主观人际咨询（同事矛盾、相处困扰等）**一律归 `其他`**，即使句中出现「同事」「部门」「上级」「争执」「不满」也不归 `人事`；提示词中显式给出判定顺序——先看是否存在制度依据，再看关键词。
- **少样本示例**：分类示例共 **15 条**（v2.1 起在基础示例上增补 4 条正负对照：同事矛盾→其他、跨部门相处→其他、员工违纪处分→人事、加班费申诉→人事；v3.2 再增补 2 条加班餐锚点），另有 3 条 `priority` 示例。
- **v3.2 归类锚点**（抑制 Q049 类模型漂移）：在规则 4 追加「食堂就餐与加班餐补贴（含加班餐标准、加班用餐补助）归 `后勤`，即使句中含『加班』也归 `后勤`」，并同步隔离「差旅伙食补助、市内交通补贴属费用报销，归 `财务`」，避免误伤原有财务类餐补题；判定规则其余文本逐字不变（由 `build_v3.py` §4.7 反证校验）。
- **规则隔离**：`priority` 判定规则前加声明「本节仅判定紧急程度，严禁据此反推或改变 `category`」，避免紧急度措辞污染分类。
- **输出解析**：使用 Dify 参数提取器（Parameter Extractor）输出结构化 `category`，并保留内置的 `__is_success` 作为失败信号接入兜底分支。

### 4.5 回答节点（llm_answer）

最高优先级规则（防幻觉护栏）：

1. 只能使用知识检索结果中的信息作答。
2. 严禁编造或推测任何制度条款、天数、金额、比例、流程步骤、时限。
3. 严禁输出任何真实电话、手机号、邮箱地址、外部网址、真实企业名称、真实人名。
4. 知识库中标注为「示例数值」的数字，回答时必须保留「示例」表述。
5. 检索结果为空、不相关或不足以支撑明确答案时，**必须且只能**输出：`暂未找到明确制度，建议转人工处理。`
6. 不得因「常识上应该如此」而补全制度细节。

`need_human` 取值规则：

- `answer` 为固定兜底话术时 → `true`
- 涉及申诉、纠纷、违规举报、紧急安全事件、个性化薪酬核算、涉密事项时 → `true`（即使知识库有相关内容）
- 其他情况 → `false`

`source` 填写规则：只能填写 `code_context` 生成的**来源白名单**中真实出现的文档名与章节标题，格式 `文档名#章节名`，多个用 `;` 分隔，无来源填 `none`，禁止臆造；v2.1 起当章节名与文档名相同时不再重复拼接（消除了 `X#X` 冗余，实测从 52 处降到 0 处）。

### 4.6 兜底链路（llm_fallback + code_fb_merge）

触发条件（`ifelse_human` 的 true 分支，OR 关系，任一命中即转人工）：

1. `code_parse.is_fallback = 1`：回答节点已输出固定兜底话术
2. `code_parse.need_human = 1`：涉及申诉、纠纷、举报、紧急安全等必须人工介入的场景
3. `code_context.retrieval_hit = 0`：知识检索无有效召回（阈值 0.5 过滤后为空）
4. `pe_category.__is_success = 0`：分类节点执行失败（模型异常 / 超时）

实现要点：固定话术由**代码节点 `code_fb_merge` 的 `FALLBACK` 常量**产出，而非 LLM 生成，确保话术逐字固定、可被脚本按字符串精确匹配；`llm_fallback` 只负责生成兜底场景的 `suggestion`，其提示词中保留「禁止修改或替换固定兜底话术」约束。

### 4.7 发布与获取 API Key

1. 点击右上角「发布 → 更新」保存工作流版本（本项目通过控制台 API `POST /console/api/apps/{app_id}/workflows/publish` 发布，可带 `marked_name` 标记版本，当前标记为 `v3.2`）。
2. 进入「访问 API」页面，右上角「API 密钥 → 创建密钥」，得到形如 `app-xxxxxxxx` 的 Key。
3. 记录 API 根地址：Dify 云端为 `https://api.dify.ai/v1`；自部署实例为 `http://<你的服务器地址>/v1`。

## 6. 评估指标

### 6.1 指标定义

| 指标 | 定义 | 关注点 |
| --- | --- | --- |
| 分类准确率（Accuracy） | `实际类别 == 期望类别` 的题数 / 总题数 | 整体路由能力，原型目标 ≥ 85% |
| 每类 Precision | 该类被判对的题数 / 判为该类的所有题数 | 高则说明误报少，工单不会错派 |
| 每类 Recall | 该类被判对的题数 / 该类实际应有的题数 | 高则说明漏报少 |
| 每类 F1 | Precision 与 Recall 的调和平均 | 单类综合表现 |
| 宏平均 F1（Macro-F1） | 6 个类别 F1 的算术平均 | 抗类别不平衡，反映整体均衡性 |
| 混淆矩阵 | 6×6 矩阵，行=期望类别，列=实际类别 | 定位具体是哪两类在互相串味 |
| 兜底率 | 回答中含固定兜底话术的题数 / 总题数 | 过高说明检索召回差或阈值过高 |
| 意外兜底数 | 非「其他」类题目却触发兜底的数量 | **关键指标**，说明知识库有覆盖缺口 |
| 关键词命中率 | `expected_keywords` 全部出现在回答中的比例 | 衡量回答内容的相关性与完整度 |
| 平均时延 | 单次 API 调用平均耗时 | 衡量线上可用性 |

### 6.2 结果解读建议

- **准确率达标但意外兜底偏高** → 知识库覆盖不足或分段过粗，检查对应文档是否缺少该小节，并尝试减小 chunk 长度。
- **某两类之间混淆矩阵数值高**（常见为 `行政` ↔ `后勤`、`人事` ↔ `IT`）→ 在 `dify_prompts.json` 的 `boundary_rules` 中补充针对性规则，并追加该场景的 few-shot 示例。
- **兜底率接近 0** → 阈值可能过低，模型在勉强作答，存在编造风险；适当提高 Score 阈值。
- **关键词命中率低但类别正确** → 分类没问题，回答节点提示词需强化「先结论后步骤」的结构要求，或提高 Top K。
- **时延过高** → 分类节点换用更轻量的模型，或关闭回答节点的多余上下文。

### 6.4 版本演进与验证结果

## 7. 可扩展方向

### 7.1 检索与知识层

- **多知识库路由**：按分类结果挂载不同知识库，减少跨域噪声。
- **父子分段 / 小召大**：用小 chunk 做向量匹配，命中后返回其所属的完整父章节，兼顾精度与上下文完整性。
- **元数据 + 时间过滤**：为制度文档增加 `版本号`、`生效日期`、`适用地区` 元数据，支持按生效版本检索。
- **混合召回调优**：Rerank（`qwen3-rerank`）已开启；下一步可用测试集对 Top K 与 Score 阈值做网格搜索，固化最优参数组合。
- **知识更新流水线**：制度文件变更后自动重建索引，并在文档中记录变更摘要，供回答引用「最新修订」。

### 7.2 工作流与业务层

- **多轮澄清**：当分类置信度低时，先反问一句澄清问题，而不是直接兜底，可显著降低意外兜底率。
- **真实工单闭环**：兜底分支接入工单系统 API，自动创建工单并回填 `ticket_id`，形成「问答 → 转人工 → 归档」闭环。
- **人工反馈回流**：对 `need_human = true` 的问题做人工标注，定期把高频缺口补进知识库，形成数据飞轮。
- **权限与身份**：接入企业 SSO，按部门 / 职级 / 地区做知识可见性隔离（如薪酬制度仅 HR 可查）。
- **多渠道接入**：通过 Dify API 对接企业 IM 机器人、内部门户、邮件网关。

### 7.3 评估与运维层

- **CI 回归门禁**：把 `run_assistant.py` 接入定时任务或流水线，准确率跌破阈值时告警。
- **扩充测试集**：将线上真实问题脱敏后加入测试集，重点补充边界与多意图问题；可增加「多意图」标签支持一题多类评估。
- **幻觉专项检测**：对回答做规则扫描（正则匹配电话、邮箱、URL、金额），命中即判定为潜在幻觉并告警。
- **A/B 对比**：同一测试集对比不同模型、不同提示词版本的指标，用数据驱动选型。
- **可观测性**：接入 Dify 的标注与日志能力，统计各节点耗时与失败率，定位瓶颈。

## 8. 常见问题

**Q：运行脚本报 401 / 403？**
A：API Key 无效或不属于该应用。请到 Dify「访问 API」页面重新创建密钥，并确认 Key 与应用一一对应。脚本对 401/403 不做重试。

**Q：脚本能连上但返回内容解析失败？**
A：多为回答节点输出了 Markdown 代码块包裹。脚本与 `code_parse` 均已内置容错清洗（纯 JSON / 代码块包裹 / 纯文本三种情况）；若仍失败，请检查 `answer_ok` / `answer_fb` 两个直接回复节点是否只引用了对应代码节点的输出、没有额外文本。

**Q：自部署 Dify 如何配置地址？**
A：`--api-url http://<你的服务器地址>/v1/chat-messages`，或设置环境变量 `DIFY_API_URL`。本项目实测地址为 `http://192.168.215.128/v1/chat-messages`（Dify 1.16.1）。

**Q：为什么很多题都走了兜底？**
A：优先检查知识库是否已完成索引、Score 阈值是否设得过高（可先降到 `0.2` 观察）、Rerank 模型是否真正生效、以及分段是否把表格切碎。

**Q：调用返回 400，错误信息是 `[Tongyi] Incorrect model credentials provided`，但密钥明明是好的？**
A：这是 Dify 把上游模型的**额度用尽 / 权限不足**错误统一包装成了「凭据错误」，文案有误导性。本项目实际遇到过：`qwen3.8-max` 额度用尽后所有调用报 400，控制台凭据校验接口还会返回底层 `401 Invalid API-key provided`。排查顺序应为：① 换一个同供应商的模型试跑（如 `qwen3.7-max`）；② 到供应商控制台确认该模型的额度/开通状态；③ 最后才怀疑密钥本身。切换模型后调用立即恢复 200。

**Q：追问场景（如「那需要提前几天？」）会不会被改写节点改坏？**
A：不会。`llm_rewrite` 的提示词强制「无历史对话时逐字原样输出」，`code_rewrite` 再加一道扩写守卫：改写后长度超过 `max(len(原句)+8, len(原句)*1.35)` 就回退原句。首轮问题实测原样透传，全量回归零回退。

**Q：v1.0 与当前 v3.2 的结构差异是什么？**
A：v2.0 在 `code_question` 之后插入 `llm_rewrite` + `code_rewrite` 两个节点（13 → 15 节点），回答节点输出从 6 字段扩展为 9 字段；v2.1 只做提示词与代码文本层面的加固，不改结构；随后把大模型节点统一切到 `qwen3.7-max`。v3.0 起扩到 **27 节点 / 32 边**：新增合规拦截、自适应检索重试、情绪识别三条链路与工单闭环，输出扩展为 **15 字段**；v3.1 修复检索相关度读取；v3.2 仅补 `pe_category` 加班餐归类锚点，**判定规则文本与拓扑均不变**。检索参数（混合检索 / Top K 5 / 阈值 0.5 / Rerank）自 v2.x 起完全一致。

**Q：v3.1 的 Q049（加班餐补）为什么判错？**
A：属模型非确定性，而非结构性回退。`cmp_pe.py` / `cmp_rw.py` 证明从 `code_question` → `llm_rewrite` → `code_rewrite` → `pe_category` 全链路相对 v2.1 逐字节一致（含模型与提示词）；`probe_q049.py` 用同一问句重复采样，同一批次内先连续判「财务」后判「人事」。v3.2 因此在规则 4 追加「加班餐补归后勤」锚点、并反向隔离「差旅伙食补助归财务」，回归恢复 65/65。

**Q：输出的 `sentiment` / `risk_flag` / `ticket_id` / `sla` 从哪来？**
A：`sentiment`（平静 / 不满 / 焦急）与 `risk_flag`（0 / 1）来自独立的 `pe_sentiment` 参数提取器节点，**不影响 `category`**；`ticket_id` 由代码节点按问题哈希生成稳定工单号（形如 `GD-XXXXXXXX`），`sla` 依 `priority` 取值（高 2 小时内 / 中 1 个工作日内 / 低 3 个工作日内响应）。

**Q：内容可以直接用于生产吗？**
A：不可以。当前所有制度内容均为示例模板，须替换为本企业经审批的正式制度，并重新评估后方可上线。
